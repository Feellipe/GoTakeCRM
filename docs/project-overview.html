9. Architectural Decisions (ADRs)

All 5 ADRs are Accepted. Source files under docs/adr/.

ADR-0001
Multi-tenant data model with single-user UI from day one
Accepted

Context

Must support two collaboration patterns: (1) freelance collab — two photographers share a specific Client subtree while keeping others private; (2) Phase 2 agency/multi-user with role-based access. Migrating a flat schema to multi-tenant later is a high-risk data migration once real data exists.

Decision

  • Every model gets organizationId from day one.
  • New tables: User, Organization, UserOrganization, ClientShare (full-subtree sharing, no per-table granular flags).
  • UI launches single-user — Organization is hidden, auto-created on signup.
  • Phase 2 adds role enforcement in middleware + UI org management; ClientShare works from Phase 1.

Consequences

+ Positive: Zero data migration to multi-user. Every query already filters by organizationId. ClientShare enables the core freelance use case immediately. Dev and prod share the same DB engine (PostgreSQL/Supabase).

− Negative: Extra field + index per model. All API routes must include organizationId even in Phase 1. SQLite can no longer be used locally — Supabase PostgreSQL required even in dev.

Risks: If Phase 2 never ships, the tenant fields are unused overhead (low — roadmap targets agencies). ClientShare may prove too coarse (can't share a Deal but hide Revenue); granular per-table sharing deferred to Phase 2.

Alternatives rejected: (a) Single-user schema, migrate later — too risky. (b) Per-table sharing flags on ClientShare — adds query complexity; use case is niche.

ADR-0002
Single-branch deployment with Vercel Preview Environments
Accepted

Context

Originally planned two Git branches (main for client, deploy/portfolio for demo) deployed to separate Vercel projects. Vercel natively supports Preview Deployments per branch with separate env vars, making branches redundant for deploy routing.

Decision

  • Single branch (main) — delete deploy/portfolio.
  • Production Deployment (from main) → gotakecrm-prod Supabase (real client data).
  • Preview Deployments (any branch push) → gotakecrm-demo Supabase (seeded demo data).
  • Env vars configured separately under Vercel "Production" and "Preview" environments.
  • Portfolio demo is simply a Preview URL shared with demo credentials.

Consequences

+ Positive: No branch maintenance / merge conflicts / schema drift. CI simplified to one branch. Same code in both envs — bug fixes ship to both simultaneously. Demo data is decoupled from code (just reseed).

− Negative: Preview Deployments are ephemeral on Hobby plan (pin a branch for persistent demo URL). Same code in both — no feature gating without flags/env checks.

Migration: Merge deploy/portfolio → main, delete branch, update CI to watch only main, configure Vercel env vars separately.

Alternatives rejected: (a) Two branches — fork maintenance trap, inevitable drift. (b) Two Vercel projects — overkill, double the dashboards/caches/pipelines.

ADR-0003
Dual auth (Credentials + Google) and unified PostgreSQL schema
Accepted

Context

CRM started Google-only via NextAuth — locked out non-Google users and put identity data in Google's systems. Project also maintained two Prisma schemas: schema.prisma (SQLite local) and schema.prod.prisma (PostgreSQL prod) — schema drift risk, dev ≠ prod DB engine.

Decision

Auth: Add CredentialsProvider (email/password, bcrypt) alongside GoogleProvider. Both coexist; users pick at sign in. User table owns data (email, name, password hash, avatar). Credentials path also enables the portfolio demo shared credential.

DB: Drop SQLite entirely — single schema.prisma on PostgreSQL. Local dev connects to gotakecrm-demo Supabase. No more schema.prod.prisma or NODE_ENV-based datasource switching. Two Supabase projects: gotakecrm-prod (Vercel Production) + gotakecrm-demo (dev + Preview).

Consequences

+ Positive: Non-Google users can sign up. Full ownership of user data. Single Prisma schema — no drift. Free to seed/mutate/test on demo Supabase. Demo reseed is one command.

− Negative: Requires internet for local dev (remote Supabase). Password hashing adds implementation surface. User table must be seeded with a demo user for portfolio preview. No offline/local-first option without local PostgreSQL.

Migration: Merge schema.prod.prisma → schema.prisma, delete schema.prod.prisma + prisma/dev.db, update db.ts, remove validate-prod-schema CI job, update vercel.json build command.

Alternatives rejected: (a) Keep SQLite for local dev — engine mismatch creates prod-only bugs. (b) More providers (Magic Link, GitHub) — deferred; Google + email/password covers the majority.

ADR-0004
WhatsApp integration via official Cloud API (one number per Organization)
Accepted

Context

WhatsApp is a core selling feature. WhatsApp has no Telegram-style "create a bot, get a token" API. Options: official Cloud API (stable, compliant, paid after free tier) vs unofficial reverse-engineered libraries (Baileys, whatsapp-web.js — free but ToS violations).

Decision

  • Use the official Meta WhatsApp Cloud API exclusively.
  • Each Organization connects their own WhatsApp Business number via Meta Business API credentials.
  • CRM stores the org's WhatsApp access token + phone number ID.
  • Incoming webhooks are routed by the phone number they arrive on → maps to Organization → processed within that org's data boundary.
  • WhatsApp groups can include the bot — all group messages route to the owning Organization.

Consequences

+ Positive: Stable, compliant, won't break overnight. Free tier covers small photographers. Natural per-org isolation via phone number. No infra cost — photographers bring their own Meta account. Scales to agency use case (one number, whole team sees messages).

− Negative: Each photographer needs a Meta Business account + WhatsApp Business number — onboarding friction. After free tier, per-message billing (cost passed through). Official API has rate limits + format restrictions. WhatsApp Business numbers can't be regular personal numbers.

Risks: Meta could change the free tier threshold. Group bot API support is limited vs DMs. Photographers in markets without WhatsApp Business API availability are blocked.

Alternatives rejected: (a) Unofficial libraries — ToS violation time bomb. (b) Single shared bot number for all orgs — destroys brand identity + routing complexity. (c) Provider-agnostic messaging layer (Telegram, IG DM) — deferred; WhatsApp is the primary market.

ADR-0005
Multi-Tenant UI Architecture
Accepted

Date: 2026-06-28 · Related: ADR-0001

Context

Multi-tenant data layer is implemented (User, Organization, UserOrganization, organizationId on all models). The UI layer needs to support: freelancers working solo AND collaborating with agencies; users with multiple org memberships; role-based access within orgs; a consolidated "All Work" view.

Decision

Navigation model — three-tier:

  1. All Work — aggregated view across ALL contexts (solo + all orgs).
  2. My Work — the user's personal workspace (always exists, no explicit org creation).
  3. Organization X/Y — specific org contexts the user is a member of.

Org state management: Active context managed via React Context + global state, NOT in the URL. Enables easy cross-org views, no URL restructuring, deep linking via session-based context.

Org switcher: Lives at the top of the sidebar, replacing the static brand section. Dropdown pattern with org name + icon + chevron.

Settings: Single page with tabs — "Personal" (persists across context switches) + a dynamic tab per org context.

Roles (per org):

RoleScope
AdminFull access to org data + configuration
AutônomoSees only clients/deals they're assigned to
CRMSees clients, conversations, proposals (read/edit) — no financials/config

WhatsApp: Configured at the user level (the photographer's number). Same bot serves all contexts. Conversation routing is role-based per org.

Consequences

Sidebar needs significant restructuring. React Context provider needed for active org state. Role gating logic needed in sidebar nav + API queries. Settings page needs tab redesign. Member management page needed. All API queries already filter by organizationId (data layer ready).

16. Technical Risks

16.1 TypeScript ignoreBuildErrors: true

next.config.ts has typescript.ignoreBuildErrors = true (and eslint.ignoreDuringBuilds = true). The production build passes even with type errors — pragmatic for rapid iteration but means type regressions can ship undetected. CI runs tsc --noEmit separately to catch them, but the deploy itself does not block on TS errors.

Mitigation: Keep tsc --noEmit in CI as a gate; track type-error count; flip to false once error count reaches zero.

16.2 No middleware.ts

Auth is checked per-route (getServerSession in every handler) rather than at the edge. Every API handler repeats session → user → org check. Risk: a forgotten check on a new route = unauthenticated access.

Mitigation: Centralize the auth helper (requireSession() / requireOrg()) and lint against direct getServerSession calls. Add middleware when role enforcement lands (ADR-0005 Phase 2).

16.3 No Server Components

Every page is 'use client'. Dashboard data flows through SWR → Context → components. Means no SSR data fetching, larger client bundles, and the initial load depends entirely on client-side SWR.

Mitigation: Acceptable for an internal CRM. Watch bundle size; consider selective Server Components for read-heavy pages (e.g. /clients list) in future.

16.4 Child-Model Tenant Isolation

Expense, Revenue, Briefing, Message have no organizationId. Tenant isolation is enforced through the Deal → Organization chain. Any query that fetches a child without first verifying the parent Deal's org leaks data across tenants.

Mitigation: Always include the parent Deal with where: { id, organizationId } before reading/writing children. Code review checklist item for any new child-model route.

16.5 WhatsApp Session Expiry

CommandSession has expiresAt with TTL cleanup (cleanupExpiredSessions.ts). If the cleanup job is not scheduled or fails, stale sessions linger and could attach a new user's input to an old session.

Mitigation: Confirm cleanup cron/Vercel Cron is wired. Defensive check on every incoming message: if expiresAt < now, delete and treat as no session.

16.6 Stripe Per-Org Credentials in DB

Each Organization stores its own Stripe secretKey, publishableKey, and webhookSecret in plaintext columns. A DB leak = full Stripe key compromise for every org.

Mitigation: Encrypt at rest (application-level AES), restrict DB access, rotate keys on incident. Long-term: use Stripe Connect (platform account) instead of per-org raw keys.

16.7 Single-Branch Demo = Same Code

ADR-0002 single-branch strategy means the demo Preview runs the exact same code as production. No way to disable a half-baked feature in demo without env-var checks or feature flags.

Mitigation: Introduce a lightweight feature-flag layer keyed off NEXT_PUBLIC_VERCEL_ENV or a flags table.
