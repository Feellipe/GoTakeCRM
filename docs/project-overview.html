/novoDeal 7 passos · cria Client + Deal + Proposta

Fluxo de passos

  1. Pedir nome do cliente (valida nao-vazio, max 200 chars).
  2. Receber nome → pedir telefone (10-13 digitos apos strip non-digit).
  3. Receber phone → listar pacotes ativos via db.package.findMany. Aborta se nenhum.
  4. Selecionar pacote (match parcial case-insensitive). Pergunta "Quer editar? (sim/nao)".
  5. Se sim: escolher valor ou descricao, captura e BRL-parse.
  6. Pergunta criar proposta (sim/nao).
  7. Persiste Client + Deal (+ Proposta se flagged), deleta sessao.

Architecture Decision Records

5 ADRs, todos Accepted. Source em docs/adr/0001-0005*.md.

ADR-0001 Multi-tenant data model com single-user UI from day one Accepted

Context

Suportar dois padroes: (1) freelance collab — dois fotografos compartilham um Client subtree mantendo outros privados; (2) Phase 2 agency com RBAC. Migrar schema flat para multi-tenant depois = migracao de alto risco.

Decision

  • Todo modelo recebe organizationId desde o dia 1.
  • Novas tabelas: User, Organization, UserOrganization, ClientShare.
  • UI inicia single-user — Organization fica escondido, autocriado no signup.

Consequences

+ Zero data migration para multi-user. ClientShare habilita freelance collab imediatamente.

- Extra field + index por modelo. SQLite nao roda mais em dev — PostgreSQL/Supabase obrigatorio.

ADR-0002 Single-branch deployment com Vercel Preview Environments Accepted

Context

Plano original: dois branches (main + deploy/portfolio) em projetos Vercel separados. Vercel suporta Preview Deployments per-branch com env vars separadas — branches redundantes para deploy routing.

Decision

  • Branch unico (main) — deletar deploy/portfolio.
  • Production Deployment → gotakecrm-prod Supabase.
  • Preview Deployments → gotakecrm-demo Supabase (com seed).

Consequences

+ Sem manutencao de branches, merge conflicts ou schema drift. Mesmo codigo em ambos os envs.

- Preview Deployments sao ephemeral no Hobby plan (pinar branch para demo URL persistente).

ADR-0003 Dual auth (Credentials + Google) e schema PostgreSQL unificado Accepted

Context

CRM comecou Google-only — bloqueava usuarios sem Google e punia identidade nos sistemas Google. Projeto tambem mantinha dois schemas Prisma (SQLite local + PostgreSQL prod) — drift risk.

Decision

Auth: Adicionar CredentialsProvider (email/senha, bcrypt) ao lado do GoogleProvider. Coexistem; usuario escolhe. Tabela User detem os dados.

DB: Dropar SQLite inteiramente — schema unico em PostgreSQL. Dev local conecta a gotakecrm-demo. Dois projetos Supabase: prod + demo.

Consequences

+ Usuarios sem Google conseguem signup. Ownership total dos dados. Schema unico — sem drift. Demo reseed = um comando.

- Requer internet para dev (Supabase remoto). Sem opcao offline/local-first.

ADR-0004 WhatsApp via Cloud API oficial (one number per Organization) Accepted

Context

WhatsApp e core selling feature. Sem API "cria bot, pega token" estilo Telegram. Opcoes: Cloud API oficial (estavel, compliant, pago apos free tier) vs bibliotecas nao-oficiais (Baileys, whatsapp-web.js — gratis mas violam ToS).

Decision

  • Usar exclusivamente Meta WhatsApp Cloud API oficial.
  • Cada Organization conecta seu proprio numero WhatsApp Business via Meta Business API.
  • CRM armazena token + phone number ID da org.
  • Webhooks sao roteados pelo phone number → map to Org → processados no data boundary da org.

Consequences

+ Estavel, compliant, free tier cobre fotografos pequenos. Isolamento natural per-org via phone number. Sem custo de infra.

- Cada fotografo precisa Meta Business account + WhatsApp Business number — friccao onboarding. Apos free tier, billing per-message.

ADR-0005 Multi-Tenant UI Architecture Accepted

Data: 2026-06-28 · Related: ADR-0001

Context

Camada de dados multi-tenant implementada (User, Organization, UserOrganization, organizationId em todos os modelos). UI precisa suportar freelancers solo E colaborando com agencies, usuarios com multiplas orgs, role-based access, e view consolidada "All Work".

Decision

Navigation model three-tier: All Work (agregado), My Work (workspace pessoal), Organization X/Y (contextos especificos).

Org state: via React Context + global state, nao na URL. Org switcher no topo da sidebar.

Roles per-org: Admin (full), Autonomo (apenas atribuidos), CRM (sem financeiro/config).

WhatsApp: configurado no user level. Mesmo bot serve todos os contextos.

Consequences

Sidebar precisa restructuring significativo. React Context provider para active org state. Role gating em sidebar + queries. Settings com tabs (Personal + dinamico por-org). Member management page. Queries ja filtram por organizationId.

Gaps & Roadmap

Prioridades: P0 blocking · P1 planejado · P2 nice-to-have.

Nao implementado

P0Real-time notifications backend
NotificationDropdown e UI only. Sem push/SSE/WebSocket. Plano: SSE em /api/notifications ou polling.
P0Org switcher UI (ADR-0005)
Three-tier nav (All Work / My Work / Org X) nao esta no sidebar. Active org via Zustand store, switcher dropdown pendente.
P0Role enforcement middleware
Sem middleware.ts — ADR-0005 Phase 2 roles (Admin/Autonomo/CRM) nao enforced server-side.
P1Mobile push (PWA notifications)
Serwist PWA install funciona, mas sem push notification permission flow.
P1Two-factor auth
Credentials + Google apenas. Sem TOTP/SMS 2FA.

Parcial

P1ClientShare UI
Schema + modelo existem (ADR-0001). Sem UI para grant/revoke cross-org sharing.
P1Proactive WhatsApp messaging
Inbound + slash-command replies funcionam. Outbound templates (reminders, marketing) nao implementado.
P2Document signing flow
Document.status enum tem draft→sent→viewed→signed, mas sem e-sign integration (DocuSign/DottedSign).
P0Member management page done
OrgMembersCard + /api/admin/organizations/[id]/members implementado.

Roadmap (planejado)

  • Phase 2 multi-user: RBAC, org switcher, "All Work" aggregated view
  • Proactive WhatsApp templates: booking reminders 24h, payment confirmations, follow-ups
  • E-sign integration: DocuSign ou DottedSign
  • Real-time notifications: SSE ou WebSocket
  • Granular sharing: per-table ClientShare flags
  • Mobile push via PWA + Web Push API
  • Provider-agnostic messaging — abstract WhatsApp para Telegram/IG DM

Riscos tecnicos

P0TS ignoreBuildErrors: true
Build passa mesmo com erros de tipo. CI roda tsc separado, mas deploy nao bloqueia em TS errors. Mitigacao: manter tsc como gate, track error count.
P0Sem middleware.ts
Auth por-rota — handler esquecido = acesso unauthenticated. Mitigacao: centralizar requireSession() + lint.
P1Sem Server Components
Toda pagina e 'use client'. Sem SSR data fetching, bundles maiores, initial load depende de SWR client.
P0Child-Model Tenant Isolation
Expense/Revenue/Briefing/Message sem organizationId. Isolamento via chain Deal→Organization. Query sem verificar parent Deal = leak cross-tenant.
P1WhatsApp Session Expiry
CommandSession tem TTL + cleanup job. Se cron falha, sessoes stale podem attachar input de usuario novo. Mitigacao: check defensivo em cada incoming message.
P0Stripe per-Org em plaintext
Cada Organization armazena secretKey/publishableKey/webhookSecret em plaintext. DB leak = comprometimento total. Mitigacao: AES at-rest, restrigir DB, rotacionar em incidente. Long-term: Stripe Connect.
P2Single-Branch = Mesmo Codigo
Demo Preview roda exato codigo de prod. Sem feature flags para desabilitar half-baked features no demo.
